# Balance

**Тема ВКР:** «Проектирование и разработка веб-приложения для самоконтроля состояния пользователя при работе за компьютером».

Одно веб-приложение для самоконтроля самочувствия при работе за экраном. React/Vite, Flask REST API, Supabase Auth и PostgreSQL. Рабочие разделы: Сегодня, Мой план, Самочувствие, Прогресс, Полезное, Работа и перерывы, Библиотека, Профиль, Администрирование.

## Запуск

```sh
npm ci
python3 -m venv backend/.venv
backend/.venv/bin/pip install -r backend/requirements.txt
npm run dev
```

`npm run dev` одновременно запускает Flask на 127.0.0.1:5001 и Vite. Откройте адрес Vite из терминала. Vite проксирует `/api` в Flask. `npm run dev:web` запускает только frontend. Не запускайте два Flask сервера на одном порту. Для Windows укажите `BALANCE_PYTHON` с путём к python виртуального окружения.

Файл `.env.local` намеренно не входит в передаваемую версию. Скопируйте `.env.example` в `.env.local` и укажите `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Backend читает эти же значения; отдельно можно задать `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`. Service role приложению не требуется и никогда не передаётся клиенту. Python проверяет TLS с сертификатами certifi. Для корпоративного сертификата можно задать `SSL_CERT_FILE`.

Внимание: SQL-файлы не полностью соответствуют текущей схеме действующей базы Supabase. Например, в `base_schema.sql` шкала боли в опросе 0–5, в действующей базе проверка 0–10; у части политик другие имена. Поэтому по этим файлам нельзя полностью восстановить проект, пока схема не сверена с дампом вашей базы. Файлы ниже применяйте как отправную точку для нового проекта. В существующем проекте все изменения применены без удаления данных; `base_schema.sql` в действующий проект не выполняйте. Порядок для нового проекта: `database/base_schema.sql`, `application.sql`, `session_continuity.sql`, `managed_zones_settings.sql`, `function_hardening.sql`, `onboarding_retry.sql`, `seed.sql`. Начальные вопросы и материалы находятся в `database/content.json`; `python3 scripts/seed.py` генерирует SQL без повторного добавления одинаковых ключей и названий. Изменения контента в админке хранятся в БД и используются при следующей загрузке.

## Как работает

- Email/пароль, подтверждение email, повторная отправка письма и восстановление пароля. В Supabase Auth должны быть включены подтверждение email и разрешены URL локального/развёрнутого приложения.
- Роли только user/admin. Обычная регистрация не даёт выбрать роль. Назначение администратора — доверенная операция оператора БД. Изменение роли через пользовательский API запрещено.
- 11 логических этапов настройки, 37 адаптивных общих вопросов и отдельная подробная оценка каждой из 10 выбранных областей. Никакого ограничения в три области. При выборе всех зон вопрос об остальных не показывается. Глаза оцениваются отдельно от карты.
- Черновик автоматически сохраняется в аккаунте и на устройстве; скрытые зависимые ответы очищаются. Завершение опроса, сохранение результатов и отметка профиля происходят одной транзакцией PostgreSQL.
- Помощник Лео работает с ИИ только при заданном `OPENAI_API_KEY` в `.env.local`. Без ключа помощник открывается, но ответы ИИ недоступны: сервер возвращает ошибку 503 с сообщением о недоступности сервиса. Подсказки по плану и остальные разделы работают без ключа.
- Движок `backend/personalization.py` учитывает ответы, последнюю запись дневника, активные правила и каталог. Каждая рекомендация содержит reason/source_factors. Это профилактическая логика, не клиническая диагностика. Ограничения не могут быть отменены обычным правилом администратора.
- Для старых анкет предложено обновление настройки. Автоматические движения не выбираются до заполнения новой версии; старые данные сохранены.
- Дневник: общее изменение отдельно от интенсивности 0–5 каждой отмеченной зоны, необязательная заметка, одна редактируемая запись на дату. Ошибки не показываются как успешное сохранение.
- Выполнение упражнений едино для плана и библиотеки, не более одной отметки на упражнение/день. Сервер проверяет актуальные ограничения, а не доверяет кнопке клиента.
- Рабочая сессия: работа/пауза/перерыв/завершение, сохранение каждые 30 секунд и на переходах состояния, восстановление после перезагрузки. Время считается по временным меткам, а не по числу срабатываний таймера. Между разделами сохраняется активная сессия. Открытая работа/перерыв продолжает считаться при закрытии вкладки до следующего сохранения состояния; завершайте сессию, если заканчиваете работу.
- Камера включается только вручную в рабочей сессии. MediaPipe обрабатывает кадры в браузере; на сервер идут лишь агрегированные счётчики. Нужны HTTPS (localhost допускается), разрешение камеры, сеть для загрузки WASM/модели. Это приблизительные напоминания, а не измерение медицинской нормы.
- Прогресс: 7/14/30/90 дней, график каждой зоны, пропуски без подстановки нулей, предыдущий период, выполненные действия, сессии и перерывы.
- Отчёт за выбранный период формируется в браузере и скачивается как PDF-файл. Название отчёта: «Отчёт о самочувствии и активности».
- Администратор управляет упражнениями, вопросами/условиями, названиями зон, дополнительными правилами, статьями, блокировкой аккаунтов, настройками и журналом. Личные анкеты/дневники в интерфейс администрирования не включены. Системные ограничения и геометрия 10 зон закреплены.

## Проверки

```sh
npm run lint
npm run typecheck
npm test
npm run build
```

9 frontend-тестов (`tests/bodyZones.test.mjs`) проверяют модели дневника, прогресса, ответов опроса и счётчиков камеры. 50 backend-тестов (`backend/test_*.py`) проверяют алгоритм плана, ограничения безопасности, валидацию ответов, права доступа и помощника. Все эти проверки используют заглушки и не обращаются к действующей базе Supabase. Браузерные тесты `tests/*.browser.mjs` не входят в `npm test` и требуют запущенного сервера разработки. `database/verify_rls.sql` проверяет отсутствие чужих данных и защиты роли в транзакции с rollback. `tests/assessment.html` — изолированный dev-стенд карты/анкеты с вымышленными данными; не входит в production build и не сохраняет результаты в аккаунте.

Ручные проверки (вход, личное пространство, мобильная ширина 390 px, переход по зонам, камера, письма, печать) не входят в автоматические тесты. В этом репозитории они не подтверждены повторно и требуют проверки на тестовом аккаунте.

## Развёртывание

Для production используйте WSGI сервер для Flask, HTTPS и reverse proxy: `/api` → backend, остальные пути → статический `dist/index.html` для SPA маршрутов. Внешний доступ к dev-серверу Flask не предназначен для production. Пример команды WSGI при установленном gunicorn: `gunicorn --bind 127.0.0.1:5001 backend.app:app`. Не передавайте серверные секреты через переменные `VITE_*`.

Неиспользуемый код прежнего прототипа удалён из передаваемой версии. В действующем приложении нет SDK Base44, фиктивных сущностей, измерений фигуры и обещаний отправки email несуществующим сервисом.

Источники начальных материалов: OSHA Computer Workstations и NHS Sitting Exercises. Контент и правила для реального медицинского использования требуют отдельной профессиональной проверки; приложение предназначено для самоконтроля и профилактических привычек.

Проверка Supabase Advisors выполнялась автором ранее и не повторялась при подготовке репозитория, поэтому её результат здесь не подтверждён. В настройках проекта, по прежним заметкам, была выключена проверка паролей по базе утечек: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection.

## Обновление UX onboarding / плана (v3)

Для уже созданной базы данных перед запуском этой версии выполните в Supabase SQL Editor:

1. `database/onboarding_v3.sql` — обновляет формулировки и варианты вопросов onboarding без удаления ответов пользователей.
2. `database/exercise_feedback.sql` — добавляет поле обратной связи после выполнения упражнения.

Для новой базы `database/application.sql` уже содержит поле обратной связи, а актуальные вопросы находятся в `database/seed.sql` и `database/content.json`.

В интерфейсе общие этапы onboarding теперь показывают по одному вопросу, BodyMap сохраняет независимую оценку каждой выбранной области, первоначальный и недельный планы объясняют причины рекомендаций, а после упражнения пользователь может отметить изменение самочувствия. «Рабочая сессия» в пользовательских текстах представлена как понятное действие «Начать работу» / «Работа и перерывы».
